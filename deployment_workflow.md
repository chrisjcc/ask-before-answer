# End-to-End Deployment and Release Workflow

This document describes the production release architecture for
AskBeforeAnswer.

The system deliberately separates the release of the trained model and
dataset from the release of the Streamlit demonstration application.

The model and dataset are published through the DVC → W&B → Hugging Face
pipeline. The demonstration application is versioned through GitHub Releases
and deployed to the Hugging Face Space through GitHub Actions.

This separation allows the model and application to evolve independently while
maintaining a clear relationship between a production model and the application
that serves it.

---

## Architectural Motivation

Our deployment pipeline is deliberately split into two distinct stages to maintain a strict "chain of custody." 

This architectural choice enforces a **human-in-the-loop** design pattern. The pipeline is heavily automated for executing sweeps, generating telemetry reports, and securely deploying the finalized assets, but it intentionally stops short of automatically selecting the "winner." 

Because the best model is often not just the one with the lowest loss (requiring qualitative evaluation of generation quality, perplexity, etc.), the system relies on the developer to review the generated telemetry reports and explicitly pull the trigger on which experiment gets promoted.

---

## 1. Architectural Overview

AskBeforeAnswer has two production release paths:

1. **Model/Data Release**
2. **Application Release**

They meet at runtime when the deployed Streamlit application loads the
production model from the Hugging Face Model Hub.

```text
                           PRODUCTION RELEASE
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                    ▼                           ▼
             MODEL/DATA RELEASE            APP RELEASE
                    │                           │
              DVC experiment               Git tag
                    │                           │
                    ▼                           ▼
             DVC promotion             GitHub Release
                    │                           │
                    ▼                           ▼
              W&B Registry            GitHub Actions
                    │                           │
                    ▼                           ▼
             HF Model + Dataset       Curated app payload
                    │                           │
                    │                           ▼
                    │                    HF Space repository
                    │                           │
                    │                           ▼
                    │                    Docker build
                    │                           │
                    │                           ▼
                    └───────────────►  Streamlit application
                                                │
                                                ▼
                                       HF model repository
```

## 2. Model Promotion Sources

When promoting a trained model to the W&B Registry using `make promote-dvc`, the system supports two distinct workflows for identifying the model you wish to deploy:

### Option A: Promoting from a W&B Sweep (e.g., `EXPERIMENT=sweep_xxxxxx`)
If your model was trained via a hyperparameter sweep (`make sweep`), DVC executes multiple trials in the background. It saves the configuration and hashes for each individual trial in hidden Git references (e.g., `refs/exps/...`) so they don't pollute your active Git branch. 

To deploy a specific trial from a sweep, you must pass the exact DVC experiment ID generated by the sweep:
```bash
make promote-dvc MODEL=sft EXPERIMENT=sweep_mmpy3u9l
```

### Option B: Promoting from Standard Development (e.g., `EXPERIMENT=HEAD`)
If you are iterating locally (e.g., just running `make train MODEL=dpo` without a sweep agent), the resulting model is tracked directly in your active working directory. Once you `git commit` those changes, the model run becomes permanently tied to your current Git branch.

To deploy the model tracked on your active branch, use `HEAD` as the experiment value. This instructs the promotion script to bypass the hidden DVC references and simply use your current Git commit:
```bash
make promote-dvc MODEL=dpo EXPERIMENT=HEAD
```
